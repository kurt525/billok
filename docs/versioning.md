# Регламент версионирования BillOK

Начальная самостоятельная версия — **1.0.0**, согласована владельцем 27 ноября 2026 года в рамках TASK-BILLOK-007 ([Issue #30](https://github.com/kurt525/billok/issues/30)). Предшествующий номер 0.8.0 унаследован от ShareTab.

| Тип   | Метка GitHub Issue | Когда применять                                                                                                       | Пример перехода |
| ----- | ------------------ | --------------------------------------------------------------------------------------------------------------------- | --------------- |
| MAJOR | `version:major`    | Несовместимое изменение или принципиальная смена модели работы/архитектуры; обязательное явное согласование владельца | 1.4.2 → 2.0.0   |
| MINOR | `version:minor`    | Новая совместимая функциональность, сохранены ранее созданные чеки и учётные записи                                   | 1.4.2 → 1.5.0   |
| PATCH | `version:patch`    | Исправление ошибки, безопасности или тестов без новых возможностей и нарушения совместимости                          | 1.4.2 → 1.4.3   |

Примеры MINOR: отдельная вкладка ссылок, переименование завершённого чека, группы участников, учёт поступлений. Примеры PATCH: исправление наложения текста, ошибочного отображения чаевых или нестабильного теста. MAJOR: несовместимая смена авторизации, формата данных или базовой модели расчётов. Размер диффа, число файлов, коммитов и Issue не определяют тип. При смешанном составе выбирается старший тип.

## Порядок выпуска

1. При подготовке нового TASK-BILLOK указать ровно одну метку версии. В Issue с MAJOR зафиксировать явное согласование владельца. Старые завершённые задачи не требуют ретроспективного повышения номера.
2. Перед коммитом реализации сверить тип задачи и текущую версию в актуальном main. Повысить выбранную компоненту на единицу и обнулить младшие. Изменить `package.json`, верхнее поле version и поле `packages[""].version` в `package-lock.json`. Не изменять версии зависимостей ради номера приложения.
3. Зафиксировать номер, тип и обоснование в описании PR вместе с `Closes #<номер Issue>`. Добавить краткую запись об изменениях в CHANGELOG.md. Повторный запуск CI, исправление ещё не выпущенной задачи и слияние PR не увеличивают версию ещё раз. Если main успел получить другой выпуск до слияния, перепроверить номер и устранить конфликт через обычный PR без переписывания истории.
4. Адресные проверки, затем полный CI 5/5 на одном SHA. После согласованного слияния действующий механизм проверяет main, совместимость и резервную копию перед production. Не менять защиту выкладки ради повышения номера.
5. Версия становится установленной на рабочем сервере после успешного развёртывания. В панели владельца номер версии читается из package.json, SHA — из идентификатора сборки. Обе величины выдаёт защищённый серверный метод admin.getSystemHealth. Не раскрывать их в публичном интерфейсе или новом публичном API.

Это регламент, а не автоматическое вычисление типа по diff. CI и система развёртывания остаются без изменений.
