# Подтверждённые метаданные установленного выпуска

## Контракт приложения (TASK-BILLOK-008)

Серверный манифест `src/server/lib/billok-release.json` включается в сборку. Он связывает версию с TASK и номером PR; изменение метаданных выполняется в том же выпуске. Ссылка строится только на PR репозитория kurt525/billok. При несовпадении версии или неверном формате сведения не отображаются.

Дата успешного развёртывания не является частью исходного кода или временем запуска. Защищённый метод `admin.getSystemHealth` читает при каждом запросе файл `/app/.billok-deployment.json` (в рабочем каталоге standalone-приложения). Ожидается обычный файл, принадлежащий root, без записи для группы/остальных, не более 4096 байт, не символьная ссылка. Пример формата (условные данные):

```json
{
  "schemaVersion": 1,
  "version": "1.1.0",
  "commitSha": "0123456789abcdef0123456789abcdef01234567",
  "deployedAt": "2026-11-27T12:00:00.000Z"
}
```

Дата принимается только при точном совпадении версии и полного SHA с запущенной сборкой, валидном времени UTC и отсутствии будущего времени. При отсутствии файла, ошибке чтения, несоответствии или повреждении — «Нет сведений». Чтение не зависит от GitHub, не требует дополнительных запросов к БД и не кэширует дату на старте.

## Предлагаемое изменение штатной выкладки — требуется отдельное согласование

На рабочем сервере `/var/lib/billok-deploy/billok-deploy.py` управляется root отдельно от репозитория. Текущий скрипт уже проверяет CI 5/5, резервную копию, совместимость исходников, SHA, здоровье контейнера, HTTPS через WireGuard и блокировку публичного доступа. Он записывает root-манифест успешного выпуска, но не передаёт время в приложение.

Предлагается исключительно дополнительная запись метаданных, без изменения условий допуска:

1. После успешных `await_container`, `probe` и `billokctl health` получить время UTC с миллисекундами; версию считать из package.json работающего контейнера, полный SHA сверить с `.commit-sha`. Записать версию и время в существующий root-манифест успешного выпуска, сохранив SHA и все прежние поля. Запись манифеста выполнить атомарно. Успех выкладки по-прежнему определяется штатными проверками, не фактом наличия маркера.
2. Передать только три несекретных значения (версия, SHA, дата) и номер схемы в работающий контейнер через существующий root-доступ Docker, без дополнительных mount, изменения прав каталога секретов или выдачи привилегий приложению. Проверить, что контейнер соответствует ожидаемым SHA и image ID, каталог /app принадлежит root и не доступен для записи непривилегированному пользователю. Создать временный обычный файл в /app с правами 0644 и владельцем root, атомарно переименовать в .billok-deployment.json; проверить чтение от UID приложения. Никогда не создавать маркер до прохождения всех штатных проверок. Если доставка метаданных не удалась, явно зафиксировать ошибку доставки; не выставлять вымышленную дату и не ослаблять защиту. Не использовать содержимое файла как входные команды.
3. При пересоздании контейнера того же SHA в ветке ALREADY_CURRENT восстановить маркер из соответствующего успешного root-манифеста. Выбирать только полностью совпадающий SHA и версию; при нескольких успешных установках — последнюю подтверждённую дату. Не менять дату при обычном перезапуске или проверке таймера. Если ранее не было сохранено подтверждённое время — оставить «Нет сведений»; не брать mtime.
4. После успешного штатного отката восстановить маркер из root-манифеста восстановленного SHA, только после проверки здоровья и сети. Не записывать дату неудавшейся выкладки. При отсутствии достоверных данных оставить дату неизвестной. Приложение дополнительно отклонит маркер другого SHA/версии.
5. Перед установкой отдельно проверить новую редакцию root-скрипта, её diff и SHA, сценарии успешной выкладки, отказа, отката, пересоздания контейнера и отсутствия маркера в изоляции. Резервировать исходный root-скрипт. Установка только после явного согласования владельца, без изменения прав доступа, Docker, CI, БД, секретов и существующих условий допуска к production.

В рамках приложения добавлен только контракт чтения и отображения. Root-скрипт, контейнер и production не изменены. До согласования и подключения механизма доставки подтверждённой даты пункт 1.2 остаётся незавершённым.
