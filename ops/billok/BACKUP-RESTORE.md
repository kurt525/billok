# BillOK: изоляция данных и проверка восстановления (Issue #1, 8.9)

Эта инструкция относится **только к BillOK**. Проект ещё не опубликован;
команды развёртывания в production здесь не выполняются. Для сетевой
публикации и TLS предусмотрен пункт **8.10**, для production-секретов —
**8.11**.

## Контейнеры и тома

В docker/docker-compose.yml сервис приложения помечен метками
ru.billok.project=billok и ru.billok.component=application. PostgreSQL и
файлы uploads находятся в **двух разных именованных томах**:

| Назначение | Том            | Каталог внутри контейнера |
| ---------- | -------------- | ------------------------- |
| PostgreSQL | billok_pgdata  | /var/lib/postgresql/data  |
| Uploads    | billok_uploads | /app/uploads              |

Каждый том имеет метки принадлежности проекту и типу данных. Нельзя
подключать тома других проектов к BillOK или удалять их через общие
команды очистки Docker.

Для общего контейнера Node.js + PostgreSQL заданы 2 GiB памяти,
резервирование 512 MiB, 2 CPU, до 256 процессов, ограничение json-file
журналов (3 × 10 MiB). Healthcheck требует одновременно работающих
PostgreSQL (pg_isready) и веб-интерфейса (/api/health). Это не заменяет
внешний HTTPS/прокси-контроль пункта 8.10.

## Резервное копирование

Бэкап создаёт scripts/ops/billok-data-backup.py. Требуется ручной запуск
**на сервере BillOK**, с Docker и Python 3. Каталог резервных копий должен
принадлежать выполняющему пользователю и иметь права 0700, файлы 0600.

Сначала следует остановить изменения чеков и uploads, например через
maintenance-режим прокси из 8.10: PostgreSQL выгружается согласованным
pg_dump, но файлы uploads копируются отдельно. При активных пользователях
это не является одной атомарной транзакцией.

Имя контейнера можно получить командой:

    docker ps --filter label=ru.billok.project=billok --filter label=ru.billok.component=application

Затем вручную выполнить с фактическим именем контейнера:

    sudo install -d -m 700 -o root -g root /var/backups/billok
    sudo python3 scripts/ops/billok-data-backup.py backup --container BILLOK_CONTAINER_NAME --directory /var/backups/billok

Скрипт откажет контейнеру без нужных меток и при неразделённых томах.
В каталоге снимка будут: database.dump (custom-формат PostgreSQL),
uploads.tar.gz и manifest.json с SHA-256 для обеих частей. Пароли не
экспортируются из контейнера и не записываются в manifest.

Снимки **содержат персональные данные** и должны храниться в защищённом
хранилище с копией за пределами VPS. Сроки хранения и расписание
автоматизации задаются после утверждения production-политики; до этого
автоматическая отправка куда-либо не выполняется.

## Проверка резервной копии

    sudo python3 scripts/ops/billok-data-backup.py verify --snapshot /var/backups/billok/BILLOK_BACKUP_DIRECTORY

Проверяются хеши файлов, архив uploads, отсутствие symlink, выходов за
пределы каталога, специальных файлов и наличие каталога receipts.

## Проверка восстановления без риска production

    sudo python3 scripts/ops/billok-data-backup.py drill --snapshot /var/backups/billok/BILLOK_BACKUP_DIRECTORY

Это **не восстановление действующего сайта**. Скрипт создаёт новый
временный PostgreSQL-том и отдельный новый том uploads с меткой
billok.ci.ephemeral=true, запускает PostgreSQL 16 без сети, выполняет
pg_restore и проверяет прикладные таблицы, распаковывает uploads в другой
том. После проверки удаляет только **свои временные ресурсы**.

Постоянные тома BillOK при этом не используются, другие проекты не
затрагиваются. При сбое исходный архив сохраняется, процедура возвращает
ошибку. Аварийное восстановление production отдельно согласовывается с
владельцем и начинается с нового резервного снимка.

## Приёмка 8.9

- Проверка docker compose config подтверждает два тома, healthcheck,
  ограничения ресурсов и ротацию логов.
- Python-тесты проверяют разграничение проектов, контрольные суммы
  и отсутствие небезопасных записей в архивах.
- На выделенных временных ресурсах выполняется реальное восстановление
  тестовой PostgreSQL-базы и файлов uploads.
- После точечной приёмки запускаются все пять обязательных CI заданий.
  Описание и результаты остаются в PR #3, чекбокс в Issue #1.

Изоляция и резервирование не заменяют предрелизную очистку в разделе 9.
