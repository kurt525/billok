# BillOK: управление production-секретами (Issue #5, пункт 8.11)

Актуально по состоянию на 28.11.2026. BillOK работает в закрытом production по HTTPS через WireGuard. Публичный доступ к приложению заблокирован. Приложение и две отдельные базы PostgreSQL размещены на сервере приложения; выделенный CI-runner использует только изолированные тестовые данные.

Требование исходного Issue #1, пункт 8.11, перенесено в [Issue #5](https://github.com/kurt525/billok/issues/5).

## Принцип хранения

Рабочие пароли PostgreSQL и SMTP, ключи AUTH_SECRET, NEXTAUTH_SECRET и необязательный приватный ключ VAPID хранятся на сервере в защищённых файлах. Не помещать их в Git, GitHub Actions Secrets, .env, Dockerfile, аргументы сборки, Docker Compose environment или журналы. Тестовые значения CI и шаблона .env.example не являются production-секретами.

Каталоги /etc/billok/secrets и /etc/billok/secrets/postgres принадлежат root:root, права 0700. Все действующие файлы секретов принадлежат root:root, права 0600.

| Путь относительно /etc/billok/secrets | Назначение                                                                                               |
| ------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| postgres/prod.password                | Пароль роли billok_prod в рабочей БД; не менее 64 шестнадцатеричных символов нижнего регистра            |
| postgres/test.password                | Отдельный пароль роли billok_test в тестовой БД; не менее 64 шестнадцатеричных символов нижнего регистра |
| auth-secret                           | Ключ Auth.js; не менее 64 шестнадцатеричных символов нижнего регистра                                    |
| nextauth-secret                       | Ключ совместимости Auth.js; не менее 64 шестнадцатеричных символов нижнего регистра                      |
| reg-ru-smtp-password                  | Пароль почтового ящика REG.RU; непустое однострочное значение                                            |
| vapid-private-key                     | Необязательный приватный ключ Web Push; при отсутствии файла загрузчик не генерирует его                 |

Файлы должны быть обычными, непустыми, без символических ссылок. Нельзя ослаблять права для доступа SentinelX, CI-runner или непривилегированного пользователя контейнера.

## Действующая архитектура

| Среда      | Контейнер PostgreSQL | База и роль | Сеть               |
| ---------- | -------------------- | ----------- | ------------------ |
| Production | billok_pg_prod       | billok_prod | billok_pg_prod_net |
| Test       | billok_pg_test       | billok_test | billok_pg_test_net |

Обе базы работают в отдельных контейнерах PostgreSQL 16, с отдельными томами billok_pg_prod_data и billok_pg_test_data и внутренними сетями Docker без публикации портов БД. Production-приложение billok-billok-1 подключено к существующей рабочей БД; его Compose не создаёт и не инициализирует PostgreSQL.

Compose задаёт BILLOK_DB_PHASE=prod и монтирует каталог /etc/billok/secrets в /run/billok-secrets с read_only: true и create_host_path: false.

docker/entrypoint.sh подключает docker/load-secrets.sh до запуска Node.js. Загрузчик проверяет принадлежность root, права, наличие и формат обязательных секретов. Пароль выбирается по BILLOK_DB_PHASE из postgres/prod.password либо postgres/test.password. Подстановка чувствительных переменных в окружение контейнера до запуска запрещена; при нарушении контейнер завершает запуск с ошибкой.

После проверки entrypoint формирует DATABASE_URL для соответствующей внешней БД, удаляет промежуточную переменную DB_PASSWORD и запускает приложение от непривилегированного пользователя nextjs (UID 1001). Нужные секреты передаются в окружение процесса во время запуска, а не в Config.Env образа или контейнера. Процесс приложения не имеет прямого доступа к защищённому каталогу файлов.

Контекст сборки исключает локальные .env, .npmrc и файлы приватных ключей. Не передавать секреты через аргументы docker build, не включать их в образы или артефакты CI.

## Эксплуатация и восстановление

Действующие ключи уже созданы. Не выполнять повторную генерацию при обновлении приложения. При утрате файла восстановить согласованное значение из защищённой резервной копии либо отдельно согласовать ротацию с владельцем.

Замена пароля PostgreSQL требует согласованного изменения соответствующей роли в БД и файла секрета, а замена ключей Auth.js может повлиять на действующие сеансы и доступ к ранее зашифрованным данным. Пароль SMTP меняется согласованно с почтовым провайдером. Не менять production-ключи в рамках обычного релиза, проверки или исправления документации.

Предусматривать защищённое резервирование секретов отдельно от исходного кода, сборочных артефактов и общих журналов; доступ к резервным копиям ограничить. Наличие отдельной резервной копии секретов и пригодность восстановления проверяются администратором независимо от резервного копирования PostgreSQL. Не считать обычный дамп БД резервной копией файлов секретов.

Не выводить значения секретов командами cat, printenv, необработанным docker inspect или docker compose config. Не использовать set -x или sh -x при работе с ключами. Не передавать пароли в командной строке, чатах и задачах GitHub.

## Контроль без раскрытия секретов

1. От root проверить метаданные каталогов и обязательных файлов, не выводя содержимое:

   ```bash
   stat -c '%F %U:%G %a %n' \
     /etc/billok/secrets \
     /etc/billok/secrets/postgres \
     /etc/billok/secrets/postgres/prod.password \
     /etc/billok/secrets/postgres/test.password \
     /etc/billok/secrets/auth-secret \
     /etc/billok/secrets/nextauth-secret \
     /etc/billok/secrets/reg-ru-smtp-password
   ```

   Для необязательного VAPID-файла проверить те же свойства при наличии. Проверка не должна следовать по символическим ссылкам.

2. Проверить, что в environment сервиса billok отсутствуют DB_PASSWORD, AUTH_SECRET, NEXTAUTH_SECRET, DATABASE_URL, EMAIL_SERVER_PASSWORD и WEB_PUSH_VAPID_PRIVATE_KEY. Проверять только необходимые свойства через программу, которая не печатает значения.
3. Проверить фактическое read-only монтирование, отказ прямого доступа UID 1001 к каталогу и отсутствие секретов в конфигурации образов и контейнеров приложения и PostgreSQL.
4. Проверить состояние штатным контроллером: `sudo /usr/local/sbin/billokctl health`. Контроллер подтверждает изоляцию обеих БД и безопасную конфигурацию Compose; отдельная проверка обязательных production-файлов выполняется контроллером при build/start. Healthcheck сам по себе не является аудитом значений секретов.
5. В изолированной тестовой среде выполнить `python3 scripts/test_billok_production_secrets.py`. Тесты проверяют отсутствие секретов в Compose и сборочном контексте, выбор внешней БД, корректную загрузку файлов и отказ запуска при недостающих, некорректных или открытых файлах и попытке подмены окружения.
6. При заключительной проверке production сравнивать действующие секреты с текущими исходниками, конфигурацией и слоями образов, сохранившимися журналами контейнеров и развёртывания только внутри доверенного root-процесса. Выводить исключительно результаты PASS/FAIL, не значения и не строки совпадений. Не менять файлы, БД или контейнеры ради проверки. Не сканировать чужие проекты на VPS.
7. Подтвердить все пять заданий CI на одном SHA и зафиксировать результат в соответствующем PR. Не обходить действующую защиту штатного развёртывания.
