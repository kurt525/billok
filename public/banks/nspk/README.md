## Автоматизированная сверка на VPS

Сверка с eav93/sbp выполняется собственным systemd timer на VPS,
а не по расписанию GitHub Actions. Плановый запуск ежедневно в
05:20 UTC (08:20 по московскому времени).

- Скрипт scripts/ops/sbp-catalog-poll.sh использует отдельную временную
  рабочую копию репозитория и существующий Node.js 22.23.4;
  не трогает сайт, базу данных и CI runner.
- Новые участники добавляются с текстовыми метками до появления иконок.
  Устаревшие записи остаются для ранее сохранённых настроек профиля,
  но скрыты из нового выбора и помечены как неактуальные.
- Переименования обновляют названия по стабильным ID НСПК.
  Для первоначальных восьми банков сохранены внутренние ID BillOK.
- Ошибочные данные, дубликаты и массовые удаления блокируются.
  Изменение одной лишь даты обновления не создаёт коммита.
- При реальном изменении скрипт создаёт отдельную ветку и PR;
  если PR ещё открыт, используется та же ветка с очередным
  обычным коммитом. CI на self-hosted runner запускается уже
  действующим GitHub-триггером push; дополнительных CI workflow
  и GitHub-hosted runner не требуется.
- **Новая целевая модель после подтверждения владельца 29.10.2026:**
  автоматически сливать и публиковать только проверенные изменения
  JSON-каталога при успешном CI 5/5. При сбое — уведомление на почту;
  при обычном успешном обновлении уведомления не нужны. Исходный код,
  CI, зависимости и инфраструктура автоматическому слиянию не подлежат.
  **До первой публикации и приёмки BillOK нельзя запускать автоматическую
  проверку по расписанию, автослияние или автоматическую выкладку**, даже если
  CI 5/5. До этого любые обновления банков — только вручную.
  После приёмки первой публикации нужно отдельно явно разрешить автоматизацию.
  Проверка допуска по умолчанию отказывает: требуются оба доверенных
  подтверждения \`firstReleasePublishedAndAccepted\` и
  \`catalogAutomationExplicitlyEnabled\`. Их нельзя выводить из данных PR
  или успешного CI; источник — защищённое управление развёртыванием.
  **Пока автослияние и автодеплой ещё не реализованы и не включены.**
- Первый защитный этап — \`scripts/lib/sbp-auto-publish-gate.mjs\`:
  функция проверки допустимости строго ограниченного PR без каких-либо
  изменений GitHub или VPS. Она проверяет свежие SHA main/PR, повторную
  валидацию JSON, ровно один изменённый файл, отсутствие конфликтов и
  все 5 обязательных заданий CI. Автослияние, безопасное развёртывание
  с откатом и почтовое уведомление остаются следующими этапами.
- Второй подготовительный этап — \`scripts/lib/sbp-auto-publish-evidence.mjs\`:
  только чтение GitHub PR, списка файлов и последнего CI точного SHA.
  При неполных сведениях — отказ. Модуль не обращается к API слияния,
  не проверяет право активации и не запускает публикацию. До первого
  принятого релиза и отдельного разрешения автоматика запрещена.
- Третий подготовительный этап — \`scripts/lib/sbp-auto-publish-merge.mjs\`:
  только создание **плана** запроса GitHub на слияние строго проверенного
  SHA, без отправки запроса. До подготовки плана требуется приёмка первого
  релиза, отдельное включение автоматизации, успешный CI и подтверждённая
  готовность безопасной выкладки, отката и аварийной отправки email.
  План не означает, что слияние или публикация выполнены. Самого
  исполнителя автослияния и автодеплоя пока нет; ничего не включено.
- Отдельная офлайн-проверка готовности выкладки
  \`scripts/lib/sbp-catalog-deploy-readiness.mjs\` запрещает выпуск,
  если вместо образов с неизменяемым digest используется тег \`latest\`,
  если недоступен предыдущий исправный образ, нет проверенного отката,
  резервной копии и уведомления при сбое либо изменяются тома БД и загрузок.
  Она не управляет Docker; фактическая схема production ещё не принята.
- \`scripts/lib/sbp-catalog-failure-email.mjs\` — будущий обработчик аварий:
  через nodemailer отправляет **только сообщение о сбое**, с конкретным
  этапом и ссылкой на CI-журнал. SMTP-реквизиты берутся лишь из защищённых
  переменных VPS \`BILLOK_SBP_ALERT_SMTP_HOST\`, \`_PORT\`, \`_USER\`,
  \`_PASSWORD\`, \`BILLOK_SBP_ALERT_FROM\`, \`_TO\`; секреты не
  включаются в письмо. Модуль не запускается сам и ничего не отправляет
  до первого принятого релиза и явного разрешения автоматики. Реальная
  конфигурация SMTP и подключение обработчика ещё не выполнялись.
- Проверка восстановления (офлайн): scripts/lib/sbp-catalog-rollback-plan.mjs
  описывает, что делать после ошибки локальной или публичной проверки
  работоспособности: вернуть предыдущий Docker-образ с неизменяемым digest
  без изменения томов базы данных и загрузок, повторно проверить сайт и
  сообщить об ошибке, даже если откат успешен. Если откат не восстановил
  работу сайта — аварийно сообщить оператору, не делать опасных повторов.
  Проверка ничего сама не запускает; до первого принятого релиза и явного
  разрешения её решения запрещены. Исполнителя Docker-отката ещё нет.

Приёмочный офлайн-тест \`scripts/ops/sbp-catalog-poll.test.sh\` через
\`npm run sbp:sync:test\` проверяет реальную последовательность работы
скрипта на временном Git-репозитории: обновление только даты без коммита,
создание отдельного PR при добавлении банка, отсутствие дублирования
коммитов при повторном запуске и обновление существующей PR-ветки при
переименовании. Настоящие GitHub, реестр НСПК и рабочая БД не используются.

### Включение после слияния PR #3 в main

Устанавливать и включать таймер разрешается только ПОСЛЕ первого
развёртывания BillOK на рабочем сайте, его приёмки и отдельного
явного разрешения на автоматизацию. Само слияние в main недостаточно
(здесь приведены команды администратора для последующего этапа):

1. Создать системный путь /usr/local/libexec/billok.
2. Скопировать **оба** доверенных файла scripts/ops/sbp-catalog-poll.sh
   и scripts/ops/sbp-catalog-trust.sh в /usr/local/libexec/billok/
   с правами 0755. Скрипт сверки проверяет JS-файлы повторно используемой
   ветки PR по текущему main **до их запуска**. Если ветка изменена вручную
   или отстала от main по исполняемым файлам, автоматизация прекращает работу
   без коммита и требует ручной проверки. Также запрещено менять в
   автоматически созданном PR что-либо, кроме JSON-каталога:
   код, конфигурацию CI, файлы приложения и права исполняемых файлов.
   Даже внутри JSON сохраняются ранее выданные внутренние ID, ID НСПК,
   пути к локальным логотипам и источник реестра. Допустимы изменения
   названий, статуса активности и добавление новых банков.
   Дата снимка должна быть корректной, не старее принятого каталога
   и не более чем на сутки впереди времени проверки, чтобы случайная
   дата из далёкого будущего не блокировала следующие сверки.
   Скрипт также повторно проверяет полученный JSON **после загрузки
   реестра и до создания коммита**, поэтому повреждённое обновление
   не будет отправлено в отдельный PR.
   Подменённые symlink отклоняются.
3. Скопировать deploy/systemd/billok-sbp-catalog-sync.service и
   deploy/systemd/billok-sbp-catalog-sync.timer в /etc/systemd/system/.
4. Выполнить systemctl daemon-reload и
   systemctl enable --now billok-sbp-catalog-sync.timer.
5. Проверить systemctl list-timers и журнал
   journalctl -u billok-sbp-catalog-sync.service.

Пользователь службы sentinelx должен иметь доступ к GitHub
для чтения и права создания ветки и PR репозитория. Служба
использует systemd StateDirectory=billok-sbp-sync
для защищённого локального каталога задач.

До включения таймера автоматических проверок не будет.
Сверка каталога НСПК сама по себе не подтверждает наличие
банковской лицензии и возможность перевода физлицу по телефону.
